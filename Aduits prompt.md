5. SOURCE HIERARCHY

عند وجود تعارض بين المصادر، لا تستخدم قاعدة واحدة بشكل أعمى.

قيّم طبيعة الادعاء أولًا.

بشكل عام، استخدم هذا الترتيب:

TIER 1 — DIRECT ARTIFACT / RUNTIME EVIDENCE

- Actual runtime behavior
- Existing source code
- Directly inspectable design files
- Actual interaction states
- Verified system behavior

TIER 2 — RENDERED VISUAL EVIDENCE

- Screenshots
- Rendered UI
- Responsive captures
- Visible states

TIER 3 — EXPLICIT PRODUCT DOCUMENTATION

- Product specifications
- Requirements
- Written design intent
- Explicit workflow documentation

TIER 4 — AUDIT EVIDENCE

- Audit observations grounded in inspected material

TIER 5 — AUDIT INTERPRETATION

- UX conclusions
- Assumptions
- inferred problems
- proposed improvements

TIER 6 — SPECULATION

ولا تفترض أن Tier 1 يفوز دائمًا إذا كان الادعاء نفسه لا يتعلق بالسلوك.

مثال:

- سؤال بصري → Screenshot / rendered UI مهم جدًا.
- سؤال عن implementation → source/runtime أهم.
- سؤال عن intended product behavior → specification قد تكون المرجع الأعلى.
- سؤال عن UX quality → يجب دمج evidence + reasoning.

عند عدم كفاية الأدلة:

UNKNOWN / NOT ENOUGH EVIDENCE

ولا تخمّن.

Analytical Evidence

10. EVIDENCE INDEPENDENCE

لا تعتبر تكرار نفس الملاحظة من عدة Audits دليلًا مستقلًا.

مثال:

إذا قالت 7 أدوات:

«"The terminal is too dense."»

لكن الأدوات السبع رأت نفس Screenshot:

فهذا:

High Consensus / Limited Evidence Independence

وليس:

7 Independent Proofs

فرّق بين:

E0 — Single Claim

Claim منفرد.

E1 — Repeated Claim

متكرر لكن غير مستقل.

E2 — Corroborated

عدة تحليلات متمايزة تدعم الفكرة.

E3 — Independently Corroborated

مصادر مستقلة تدعمها.

E4 — Directly Verified

دليل مباشر قوي من artifact/runtime/source.

37. MANDATORY INTERNAL MULTI-PASS PROCESS

لا تنفذ المهمة كـsingle-pass answer.

نفّذ داخليًا:

PASS 1 — INVENTORY

Catalog all supplied materials.

PASS 2 — SOURCE COVERAGE

Map what each source covers.

PASS 3 — DEEP READ

Read all Audits and inspect all usable design artifacts.

PASS 4 — VISUAL / STRUCTURAL INSPECTION

Inspect screenshots, files, hierarchy, layout and visible behavior.

PASS 5 — EXTRACTION

Extract all meaningful findings, strengths and recommendations.

PASS 6 — CLUSTERING

Group semantically related findings.

PASS 7 — DEDUPLICATION

Merge duplicates without losing nuances.

PASS 8 — CANONICALIZATION

Create Canonical Finding IDs.

PASS 9 — TRACEABILITY

Attach sources and evidence.

PASS 10 — EVIDENCE CLASSIFICATION

Classify evidence type, quality and independence.

PASS 11 — CONSENSUS ANALYSIS

Evaluate consensus without treating it as proof.

PASS 12 — CONTRADICTION DETECTION

Actively search for conflicting conclusions.

PASS 13 — PRODUCT-FIT TEST

Evaluate workflow, learning, identity, accessibility and implementation fit.

PASS 14 — COUNTERARGUMENT TEST

Try to disprove major recommendations.

PASS 15 — DESIGN SYSTEM SYNTHESIS

Convert systemic problems into systemic decisions.

PASS 16 — SCREEN SYNTHESIS

Map decisions screen-by-screen.

PASS 17 — RESPONSIVE + ACCESSIBILITY REVIEW

Verify cross-device consistency.

PASS 18 — PRESERVATION REVIEW

Ensure strong existing design is not accidentally removed.

PASS 19 — AUDIT GAP REVIEW

Search for missing problems and valid NEW INSIGHTS.

PASS 20 — PRIORITY RE-EVALUATION

Recalculate priority after conflict resolution.

PASS 21 — COVERAGE GATE

Ensure every meaningful source finding has a disposition.

PASS 22 — ADVERSARIAL REVIEW

Act as a Principal Product Designer trying to reject unnecessary changes.

PASS 23 — TRACEABILITY GATE

Check:

Observation → Evidence → Interpretation → Decision → Action

PASS 24 — FINAL CONSISTENCY GATE

Check:

- No duplicate findings
- No contradictory decisions
- No false consensus
- No false dissent
- No unsupported claims
- No hallucinated requirements
- No invented engine semantics
- No accidental architecture redesign
- No loss of identity
- No important source ignored
- No critical area missing

- Invent product requirements
- Invent engine semantics
- Treat audit repetition as proof
- Treat model reputation as evidence
- Hide minority insights
- Delete findings merely because they are inconvenient
- Create duplicate findings
- Turn uncertainty into certainty
- Redesign for novelty
- Destroy existing strengths
- Over-gamify the product
- Turn the terminal into a dashboard card
- Add metrics without meaning
- Change architecture without evidence
- Assume mobile is desktop scaled down

Always:

- Inspect the original artifacts
- Use screenshots as visual evidence
- Use source/runtime evidence where available
- Use Audits as analytical evidence
- Preserve traceability
- Preserve useful disagreements
- Resolve contradictions
- Separate fact from interpretation
- Prefer evidence quality over consensus
- Prefer independent corroboration over repetition
- Make decisions explicit
- State uncertainty honestly
- Protect product identity
- Preserve strong existing design
- Produce implementation-ready decisions

41. FINAL MASTER PRINCIPLE

The quality bar is not:

«"Did I combine the nine Audits?"»

The quality bar is:

«"Did I extract the strongest valid insight from every supplied source, verify it against the original design evidence, eliminate duplication, resolve contradictions, preserve minority insights when justified, reject weak recommendations, identify legitimate missing issues, and produce one coherent design truth for AeroBridge without inventing anything?"»

The final product should feel like:

«Premium airline training workstation that happens to use a modern interface — not a dashboard that happens to contain aviation content.»

And the ultimate rule is:

«The UI may interpret engine state, but it must never invent engine truth.»

«Evidence quality beats consensus.»

«Independent corroboration beats repetition.»

«One root problem = one Canonical Finding.»

«Preserve what is strong unless there is a clear evidence-based reason to change it.»

«When evidence is insufficient, say UNKNOWN / VALIDATION REQUIRED.»

Your final deliverable is:

A DEFENSIBLE, TRACEABLE, EVIDENCE-WEIGHTED, CONFLICT-RESOLVED, HIGH-COVERAGE, IMPLEMENTATION-READY UNIFIED DESIGN AUDIT.

Do not produce a summary.

Do not produce an opinion dump.

Do not produce a vote.

Do not produce a collection of nine reports.

Produce one coherent, comprehensive, evidence-driven design authority for AeroBridge.
