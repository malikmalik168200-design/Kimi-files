# AeroBridge Comprehensive Professional Design/UX Audit

## 1. Executive Assessment

**Current product level:** A high-fidelity, visually mature single-page prototype that already communicates a distinctive, defensible identity — the "Flight Deck Console" (deep navy, Vector Blue accents, green/amber operational states, monospace readouts, terminal-first Practice). It is clearly above generic SaaS-template quality and reads as intentional, cinematic, and operational. The design language is coherent across five routes.

**Strongest existing qualities (keep):**
- A genuinely cohesive visual system with a single accent hue and disciplined status semantics (`index.css` `:root` tokens, lines 7–35).
- Consistent, purposeful motion that is *fully* gated behind `prefers-reduced-motion` in every animation block (CSS lines 123, 217, 228–231, 246, 251, 256, 266, 271, 275, 280, 293, 302).
- Honest labeling of mock behavior in the Terminal: "LOCAL TRAINING SIMULATION", "RESPONSE MODEL / ILLUSTRATIVE · VERIFY WITH YOUR COURSE MATERIAL" (`Home.tsx` line 304). This is exactly the right instinct for a prototype.
- Real accessibility groundwork in places: chart has a `<details>` data-table alternative (line 206), `AnimatedNumber`/`ProgressRing` carry `aria-label`s (lines 136, 149), `aria-live` on terminal history and the assessment report (lines 304, 236).

**Biggest risks / gap to the intended workstation:**
1. **Typography is too small to be a professional long-session workstation.** Pervasive 8–10px labels (eyebrow 9px → 8px → 7px; terminal body 11px → 10px on mobile). This is the single largest gap between "looks premium in a screenshot" and "usable for hours of training."
2. **The Arabic / mixed-language dimension central to the Saudi-market mission is unimplemented.** The EN/AR switch is a `toast` only (line 164); no RTL, no `dir`, no Arabic content, despite a `--font-ar: Cairo` token (CSS line 33).
3. **Several visible controls are non-functional stubs** (search, profile, "My route", "Filters", "Backup", "See all stages", "View map") that fire `toast.info`. The mission explicitly requires every element to be load-bearing.
4. **A real layout bug:** the mobile bottom nav renders 5 items into a 4-column grid (`Home.tsx` line 184 vs `index.css` line 118).
5. **Terminal has no loading/processing/interrupted/error-recovery states** and an empty-submit silently executes `FQD` (line 275) — a functional-safety concern for the later engine.

**Verdict preview:** The prototype is a strong *visual* foundation that needs a **focused revision pass** (typography/contrast/touch-targets, honest mock labeling, bottom-nav fix, Terminal state language) before it becomes an implementation-ready spec for the real engine. It does **not** need foundational architecture rework of its *visual* layer. See §14.

## 3. Current Product and Information Architecture

**Routing model:** Manual history routing, not a router library. `Home` holds `view` state; `navigate()` calls `window.history.pushState` and maps path→view via `pathToView` (`Home.tsx` lines 351–360). Five views: `progression | practice | scenarios | growth | tracking`.

**The intended loop** (`Progression → Practice → Assessment → Growth → Tracking → Scenarios → Next Action`) maps to the code as:

| Loop stage | Where it lives | Strength of transition |
|---|---|---|
| Progression (orient + next action) | `Progression` (L215) — hero "Resume pricing workflow" → Practice | **Strong** — one clear primary CTA into Practice |
| Practice → Assessment | `Practice` (L239), `mode` tabs learn/practice/assessment | **Strong** conceptually; **weak** state hygiene (mode switch doesn't reset history) |
| Assessment → Growth/Tracking | Finish session → `saveAssessment` → localStorage → Tracking/Growth read it (L306, 358) | **Strong** — evidence genuinely flows through |
| Growth (interpret evidence) | `Growth` (L338) + `learning-loop-strip` (L343) | **Medium** — good "read → practice → apply" strip, but many stub actions |
| Tracking (trend + next action) | `ProgressTracking` (L192) with metric switcher + "Open targeted practice" | **Strong** — closes back into Practice |
| Scenarios (apply) | `Scenarios` (L321) | **Medium** — selection works; Start/Resume/Review closure partly stubbed |
| Next Action | Present on Tracking/Growth; Scenario→Practice via `setPracticeContext` | **Medium** |

**Assessment:** The loop is genuinely wired end-to-end for the core path (Practice assessment → localStorage → Tracking/Growth read-back). This is the prototype's best structural asset and must be preserved. The weak points are (a) contextual "next action" that sometimes routes to `toast` stubs rather than the actual next surface, and (b) the boundary between real local evidence (the saved records) and hardcoded illustrative metrics (footer "128/210", task "68%") is invisible to the user.

## 6. Terminal Deep Audit (the heart of the product)

**Layout & hierarchy (L302–308, CSS 110/235–250):** The terminal is a distinct, high-contrast panel (`#040a14`, cyan border, inset glow) with a clear head → body → input → footnote stack. On desktop the coach is a sticky sibling column (CSS 126 `practice-layout` 1.35fr/0.65fr); focus mode promotes the terminal to a full-viewport overlay (CSS 237). **This genuinely reads as the primary workstation, not one card among many.** Keep this.

**Answers to the required Terminal questions:**

1. **Does it feel like the primary workstation?** Yes. Dedicated panel, focus mode, session readout, footer metrics. Confirmed by CSS 110/237. *Keep.*
2. **Session state understood in seconds?** Partially. `terminal-session-readout` shows SESSION / COMMAND / LOG state (L303) — good — **but it is `display:none` on mobile** (CSS 242), removing the primary state indicator exactly where screen space already forces prioritization. **Finding F-09.**
3. **Is command input easy to find?** Yes on desktop; on mobile it's sticky with `font-size:16px` (prevents iOS zoom, CSS 212/236) and safe-area padding — well done. Minor: the body's `terminal-active-line` mirrors the typed text (`{command || "_"}`, L304) *above* the actual `<input>`, creating two live cursors. Realistic but potentially confusing. *Observation.*
4. **Relationship between output / input / history / feedback / reference / coach / assessment closure clear?** Mostly. History is a labeled list with left-border command rows (CSS 236). Coach is separate. Reference is an inline drawer. Assessment closure is the `terminal-finish` button → report. **Gap:** in `assessment` mode the coach still renders a panel (L311) and the footnote flips to "HINTS SUPPRESSED" (L306) — good — but switching modes does **not** clear `commandHistory`/`hintCount` (L301 only resets `sessionComplete`), so evidence from Practice can bleed into an Assessment score. **Finding F-06 (State-dependent).**
5. **Are success/error/warning/invalid/processing/interrupted states distinguishable without color?** **No, incompletely.** Success/error use color plus text ("SEGMENT SOLD…", "SYNTAX ERROR…") — the text carries meaning, which is good. **But there is no processing/loading state at all** (commands resolve synchronously, L289–296), **no interrupted state**, and success vs error in the history row is signaled primarily by color class (`terminal-success`/`terminal-error`, L304) without an icon or glyph. Add a non-color marker (e.g., `OK` / `ERR` glyph or the existing error-taxonomy dot) to each row. **Finding F-05.**
6. **Is long-session reading comfortable?** **Weak.** Terminal body is 11px desktop / **10px mobile** with `line-height` reduced to 1.75 on mobile (CSS 243). For a workstation meant for extended EgyptAir-style drills, this is below comfortable. Raise to ≥13px desktop / ≥14px mobile for command/output text. **Finding F-01.**
7. **Does mobile preserve output → input → session state → feedback order?** Order is preserved (body scrolls, input sticky), **but session-state readout is hidden on mobile** (CSS 242) and the coach panel drops below the fold. Critical feedback (coach "next move") is far from the command line on mobile. **Finding F-09.**
8. **Are any "Terminal enhancements" actually Engine/Data/Content dependent?** Yes — flag clearly so the later engineer doesn't fake them:
   - Realistic command parsing/validation beyond the 4 hardcoded prefixes (AN/SS/FQD/FXP, L280–288) = **Engine dependent.**
   - Real fare/availability output = **Data/Content dependent.**
   - Processing latency/spinner = **UI-only** (can be a pure visual state) *unless* tied to real async engine calls (then Mixed).
   - Command history persistence across sessions = **State/Data dependent.**

**Additional Terminal findings:**
- **Empty submit executes `FQD`** (`command.trim().toUpperCase() || "FQD"`, L275). Submitting nothing should be a no-op or an inline "enter a command" hint, never a silent real command. **Finding F-04 (Mixed — touches command handling; must be specified carefully so it doesn't alter real engine semantics).**
- **Reference-open increments `hintCount`** in learn *and* practice modes (L303); repeatedly toggling inflates the hint penalty, and merely consulting reference in *Learn* mode arguably shouldn't be penalized at all. **Finding F-07 (State-dependent).**
- **Coach reveals the "next useful move" even in Practice** (L311, `coachState.next`) — verify this matches the intended hint-discipline model; it may be intended, so flagged as **open question**, not a defect.
- Focus mode uses `body:has(.focus-mode)` to lock scroll (CSS 200) — modern-browser dependent; acceptable, note as validation-needed on older Safari.

## 7. Shared Design System Audit

**Tokens (CSS 7–35):** A compact, sensible token set (navy scale, line, text tiers, accent hues, panel, shadow, radius, ease, three font families). This is the system's backbone — **keep and formalize**.

**Gaps to specify:**
- **Type scale is undefined.** Font sizes are ad-hoc literals from 7px to 42px scattered across 400 lines. There is no `--text-xs/sm/base…` scale, so the "too small" problem has no single lever. **Specify a documented type scale with an enforced ≥12px floor for metadata and ≥14px for reading text.**
- **Radius tokens bypassed.** `--radius:16px` / `--radius-sm:11px` exist (CSS 29) but most components hardcode `border-radius: 9px/10px/11px/12px/14px/18px/20px/24px` (e.g., CSS 105, 236, 283, 287, 296). Consolidate to a radius scale.
- **Spacing is entirely magic numbers** (`gap:8px/11px/13px/14px`, `padding:9px/10px/11px/13px/18px`). Define a spacing scale (4/8-based) and map existing values to it.
- **No focus-ring token consistency:** two different focus colors are used — global `outline: 2px solid var(--cyan)` (CSS 42) vs component `outline: 2px solid var(--blue-bright)` (CSS 265). Pick one.
- **Status system is solid** (green/amber/red/violet/cyan with `StateNotice` variants, CSS 305–308, and an error taxonomy legend, CSS 308) — **keep**; extend it to cover the *typed-but-unrendered* states (see below).
- **Elevation/surface:** `panel-surface` (CSS 69) is the reusable card; but Tracking/Growth introduced bespoke gradient/guilloché surfaces (CSS 287–296) that diverge from it. Reconcile into 2–3 named surface tiers.
- **Buttons/inputs:** `primary-button`, `ghost-button`, `icon-button`, `text-action`, `terminal-input button` are consistent and have active/hover/focus states (CSS 74–77, 265). Touch target sizing needs a minimum (see §8).
- **Motion:** ease token + reduced-motion coverage are excellent; formalize durations (160/180/220/240/260/280/300ms are all in use) into 2–3 tokens.
- **Breakpoints:** 480, 739/740, 1100, 1450 — document these as named tokens; they're used consistently.

**State language coverage:** `SystemState` (L39) enumerates 14 states but the UI only implements ~6 (empty, error, review, completed, retry, current/locked). `loading`, `first-use`, `in-progress`, `partial-success`, `interrupted`, `unavailable` are typed but never rendered. Specify a canonical component per state so the later engine can attach to them.

## 10. Target-State Design Revision Specification (no code)

**Design principle:** Preserve the Flight Deck Console identity and the working evidence loop. Change the *reading layer* (type, contrast, targets), the *honesty layer* (mock/real, stubs), and the *state completeness* of the Terminal — nothing about command semantics, scoring math, or route structure.

1. **Type system.** Introduce a documented scale. Reading/command/output text ≥14px mobile and ≥13–14px desktop; metadata/eyebrow floor 12px (never 7–10px). Preserve monospace for commands, codes, fares, dates, and readouts; use the display sans for prose/headings. Retain tabular-nums for all metrics (already present, CSS 220). Keep the visual rhythm by scaling containers, not by shrinking text.

2. **Contrast.** Raise faint/muted tiers so all text meets AA at its rendered size (≥4.5:1 for <18px). `terminal-muted` metadata must clear AA against `#040a14`. Keep the palette hues; adjust luminance only.

3. **Terminal state completeness.** Add explicit, non-color-dependent states: `ready`, `processing` (visible pending indicator on Execute), `success` (glyph + green), `error` (glyph + red + recovery hint), `invalid/syntax` (with the existing taxonomy dot), `interrupted` (session paused/lost), and `empty` (no command entered → inline prompt, never auto-`FQD`). Each history row carries a text/glyph status token in addition to color. Keep "LOCAL TRAINING SIMULATION" labeling.

4. **Assessment integrity.** Switching modes prompts/clears the working session deterministically so Practice evidence cannot count toward an Assessment score. Hint accounting: consulting Reference in Learn mode is not penalized; in Practice it counts once per *distinct* consult, not per toggle; in Assessment it stays suppressed (as today).

5. **Mock/real boundary.** Every hardcoded illustrative metric (footer 128/210, task 68%, scenario 23/40 & 82%, pre-command accuracy 86%) is visibly marked as illustrative/local, or removed, so only genuine localStorage-derived evidence is presented as the trainee's data.

6. **Honest controls.** Search, profile, "My route", "Filters" (duplicate of the working filter tabs), "Backup", "View map", "See all stages" are either wired to real destinations/behaviors or demoted from buttons to labels / hidden in the preview. No control claims an action it does not perform (esp. "Backup created").

7. **Navigation & shell.** Fix bottom-nav to fit its item count (5-col or a defined primary slot) and either implement or remove `is-primary`. Add `<main>`, a skip link, `aria-label` on side `<nav>`, `aria-current` on side-nav active item. Convert the mobile drawer to a proper modal dialog (focus trap, Escape, `aria-modal`, focus restore).

8. **Curriculum framing.** Surface EgyptAir **Basic vs Advanced** explicitly in Progression (grouping) and Growth (readiness), tied to the existing "Saudi readiness" signal. This is content structure, not new metrics.

9. **Arabic / mixed-language.** Specify (do not fake) an i18n/RTL plan: `dir`/`lang` handling, Cairo for Arabic, mirrored layout, and mixed-direction handling for aviation codes/commands (which stay LTR/monospace inside RTL prose). Flag as a dependency, not a quick toggle.

10. **Decoration discipline.** Reduce the Tracking KPI guilloché/clip-path ornament to keep the primary readout instrument-like; move the hover-only skill coaching into the persistent selected-skill panel so mobile has parity.

11. **Touch targets.** All interactive controls ≥44×44px (or ≥40px with adequate spacing) at every breakpoint, including icon buttons, filter tabs, and text actions.

## 12. Acceptance Criteria (measurable)

**Terminal**
- No command executes on empty submit; empty submit shows an inline prompt and changes no state (replaces L275 `|| "FQD"`).
- Every history row conveys success/error/invalid via text or glyph **and** color (verified with a grayscale screenshot).
- A visible `processing` state exists between submit and result; `interrupted` and `empty` states render.
- Command/output text renders ≥14px on mobile and ≥13px on desktop.
- Session-state readout (SESSION/COMMAND/LOG) remains visible on mobile in some form.
- Switching modes cannot carry prior-mode command history into an Assessment score (verified by switching Practice→Assessment and confirming a clean session).

**Navigation**
- Bottom nav shows all 5 destinations on one row at 320–430px with no wrap/overlap.
- Desktop side-nav active item exposes `aria-current="page"`; side `<nav>` has an `aria-label`.
- A skip link moves focus to `<main>`; `<main>` exists and wraps page content.
- Mobile drawer traps focus, closes on Escape, sets `aria-modal`, and restores focus to its trigger.

**States**
- Each of the 14 `SystemState` values either has a defined rendered treatment or is documented as intentionally unused.
- Empty states exist for: filtered Scenarios (no matches), empty Tracking, empty Growth (already present — keep).

**Design system**
- A single type scale, spacing scale, radius scale, and one focus-ring token are defined and used; no reading text < 12px remains; no bespoke radius outside the scale.

**All screens**
- No control performs a `toast`-only pretense of a real action; "Backup" no longer claims persistence it doesn't provide.
- All hardcoded illustrative metrics are visibly marked local/illustrative or removed.

**Responsive**
- Verified layouts (no overflow/clipping/sub-12px reading text) at 1450, 1280, 1024, 768, 430, 390, 360, 320px.

**Accessibility**
- All text meets WCAG AA contrast at its rendered size (automated + spot manual check).
- All interactive targets ≥44×44px (or ≥40px with spacing) at every breakpoint.
- Reduced-motion continues to disable all animation (regression check — currently passing).

**Motion**
- No new animation is exempt from `prefers-reduced-motion`.

**Regression safety (prove nothing functional changed)**
- The four recognized command prefixes (AN/SS/FQD/FXP) and their responses/scoring (L280–296, `assessmentScore` L48–57) produce identical outputs before/after the visual pass.
- localStorage key `aerobridge-progress-records` schema, seeding (L355–358), and read-back on Tracking/Growth are unchanged.

- The Progression→Practice→Assessment→Growth/Tracking→Scenarios flow performs identically.

## 14. Final Verdict

**The prototype needs a focused revision pass — it is not yet an implementation-ready spec, but it is close and its foundation is sound.** The visual identity, the end-to-end evidence loop (Practice → localStorage → Tracking/Growth), the motion discipline, and the Terminal's central role are genuine assets that should be preserved verbatim. What stands between "beautiful prototype" and "professional aviation training workstation" is a bounded, mostly **UI-only** set of fixes: a real type/contrast/touch-target baseline, completion of the Terminal state language, removal of pretend controls and unmarked mock metrics, the bottom-nav bug, and shell-level accessibility (landmarks, skip link, dialog semantics). 

Two items require **product/architecture clarification before UI work, not UI invention**: the Arabic/RTL mission requirement (currently absent) and the EgyptAir Basic/Advanced curriculum + Saudi-readiness model (currently illustrative). Everything else can proceed in the P0→P3 sequence in §11 without touching command semantics, scoring math, persistence schema, or routing — satisfying the clean-separation constraint so the audited design can later be applied to your real vanilla engine safely.
